
# ReCAP：基于阶段间合同的 ReAct Agent 合规护栏

## 1. 核心背景与问题

### 1.1 背景与局限
在 ReAct（Think-Act-Observe）循环中，现有 Agent 护栏通常只进行单阶段风险检测（如仅检查输入提示词、单个工具调用的合法性或输出内容）。这种方式容易忽略**跨阶段语义不一致**引发的安全隐患：
- **Think → Act 承诺违背**：例如 Agent 思考时承诺“仅将报告发给内部部门”，实际调用邮件工具时却填入了外部邮箱。
- **Observe → Think 目标劫持**：例如 Agent 读取了包含恶意指令的外部邮件后，在下一轮思考中将不可信数据误当作高权限控制指令，从而篡改了原始任务。

### 1.2 核心研究切入点
ReCAP 不关注单阶段的静态打分，而是关注：**如何显式表示并在线验证 ReAct 相邻阶段之间的语义契约关系，实现跨阶段的承诺兑现、权限约束与证据追溯。**

### 1.3 核心贡献
1. **跨阶段契约范式**：将 ReAct 安全检查从单阶段分类推进到“承诺-执行-效果-证据”的关系验证。
2. **ReCAP 护栏架构**：提出由“公开意图证书”、“共享契约账本”与“三类转换检查”构成的运行时防护机制。
3. **解释性与恢复机制**：基于冲突约束生成可重放的最小违规证据链，并支持精确的分类恢复。

## 2. 核心架构与方法

ReCAP 作为外部运行时层插入 ReAct 循环，无需修改大模型参数，在每次阶段转换时进行在线校验。

```
[User Task & Policies]
         │
         ▼
[Think] ──(提交意图证书)──► [Think→Act 检查] ──► [Act (工具调用)]
                                                       │
[Think (下一轮)] ◄── [Observe→Think 检查] ◄── [Act→Observe 检查]
                                                       │
                       ┌───────────────────────────────┴┐
                       ▼                                ▼
              [共享契约与证据账本] ◄───────► [可重放违规证据链]
```

### 2.1 公开意图证书 (Public Intent Certificate)
 Agent 在 Think 阶段需显式提交结构化契约承诺（包含 6 维字段）：
- **当前子目标**：本轮具体任务；
- **拟执行操作**：准备调用的工具/动作；
- **参数约束**：允许处理的数据范围、操作对象及接收方；
- **授权依据**：用户指令或政策凭证；
- **预期效果**：允许和禁止产生状态变化；
- **所需证据**：执行后必须获得的回执或来源证明。

### 2.2 三类阶段转换检查

#### ① Think → Act 检查：承诺兑现
在工具执行前，比较意图证书与实际工具调用参数：
- 校验实际动作是否偏离声明的子目标；
- 校验具体参数（收件人、文件路径、金额等）是否落在证书允许的约束范围内；
- 拦截不必要的高权限或越权操作。

#### ② Act → Observe 检查：真实绑定与证据校验
在环境返回结果时：
- 将 Observation 强绑定到具体的工具调用 ID 和参数摘要，防止结果串线；
- 校验环境真实状态变化（状态差分）是否符合预期，以及回执证据是否完备；
- 为返回的数据标记来源与信任等级（第三方数据标记为低信任）。

#### ③ Observe → Think 检查：隔离间接提示注入
在 Agent 进入下一轮思考前：
- **区分事实与指令**：仅允许低信任数据提供“事实信息”，禁止其发布“控制指令”；
- **阻断无授权越权**：阻止外部数据随意改变任务目标或扩大工具权限；
- **数据净化**：剔除恶意指令，保留带有来源标签的数据事实供后续规划使用。

### 2.3 共享契约与证据账本 (Ledger)
账本在整个轨迹中持续维护：当前目标、提交的意图证书、已用授权、未完成义务、历史工具调用及 Observation 信任标记。它使三个阶段共享统一且可验证的动态约束，而非无序的风险分数。

### 2.4 违规证据与恢复机制
当规则冲突时，系统提取导致冲突的**最小事实集合**生成可重放证据链，并根据违规位置执行对应恢复策略：
- **意图违规**：拒绝证书，要求在约束下重新规划；
- **动作违规**：执行前阻断，或自动收缩/修复超纲参数；
- **返回污染**：净化 Observation 并隔离恶意指令；
- **证据不足**：保持未完成状态，禁止 Agent 虚假宣布成功；
- **高风险未知操作**：阻断并升级至人工审批。

## 3. 具体实现方案

### 3.1 系统模块

第一版可以使用 Python 实现，并在现有 ReAct Agent 与工具环境之间加入一个运行时中间层。该中间层由六个模块组成：

1. **ReAct Runner Adapter**：拦截模型输出、工具调用和工具返回，不直接改动模型参数；
2. **Policy Compiler**：把 benchmark 自带的安全规则、用户授权和工具权限整理成有限的机器可执行规则；
3. **Semantic Normalizer**：用 LLM 或小型分类器把自然语言整理成实体、操作、参数、权限、效果和来源等固定字段；
4. **Transition Verifier**：在三个阶段转换点执行约束检查；
5. **Trusted Tool Wrapper**：实际调用工具，并记录调用 ID、参数摘要、返回格式和可观测的状态变化；
6. **Ledger and Recovery Manager**：维护共享账本，生成违规证据，并执行阻断、净化或重新规划。

结构化数据可以使用 JSON Schema 或 Pydantic 校验，账本原型可以存入 SQLite，并额外导出 JSONL 轨迹便于实验重放。约束验证第一版统一使用 Z3 即可，不必同时引入多套规则引擎。

### 3.2 统一数据格式

为了让三个阶段能够连接起来，每一步至少维护三类结构化事件：

- **Intent Event**：保存公开意图证书、当前轮次和授权依据；
- **Action Event**：保存工具名、真实参数、调用 ID、参数摘要和执行状态；
- **Observation Event**：保存对应调用 ID、返回内容、状态差分、证据、数据来源和信任等级。

例如，模型在准备调用工具时，不只输出工具名和参数，还需同时输出一份结构化意图：

```json
{
    "subgoal": "将审计报告发送给内部审计部门",
    "proposed_operation": "send_email",
    "argument_constraints": {
        "recipient": {"operator": "eq", "value": "audit@company.internal", "value_type": "email"},
        "attachment": {"operator": "in", "value": ["audit_report.pdf"], "value_type": "enum"}
    },
    "authority_basis": "user_request",
    "expected_effect": "新增一封内部邮件",
    "required_evidence": ["delivery_receipt"]
}
```

`argument_constraints` 采用**键值对标准**：键来自固定有限集合（`ConstraintField`，如 `order_id` / `recipient` / `attachment`），值为一条 `Constraint` 对象 `{"operator", "value", "value_type"}`。其中：

- `value_type` 仅限 `number` / `email` / `enum` / `bool`（禁止自由字符串——字符串标识符须用 `enum` 显式列举）；
- `operator` 仅限 `eq` / `ne` / `ge` / `le` / `gt` / `lt` / `in` / `not_in` / `regex` / `expr`，且受 `value_type` 限定合法组合（数值比较仅用于 `number`，集合包含与正则用于 `email`/`enum`，沙箱表达式 `expr` 用于复杂条件）。
- `authority_basis` 受控词表：`user_request` / `policy` / `system` / `user_authorization` / `verified_session`。

适配器先解析并校验证书，再决定是否允许随后的工具调用。证书解析失败、关键字段缺失或语义抽取置信度过低时，系统要求 Agent 补充信息或重新规划，而不是默认放行。

### 3.3 一次完整运行流程

系统可以按照以下顺序工作：

1. **初始化任务**：读取用户目标、benchmark policy、工具列表和初始权限，写入账本；
2. **生成意图**：要求 Agent 输出公开意图证书和候选工具调用；
3. **执行 Think→Act 检查**：验证目标、操作、参数和权限；只有通过后，工具调用才会被发送给环境；
4. **可信执行**：工具包装器生成唯一调用 ID，记录参数摘要，并在条件允许时采集执行前后的状态；
5. **执行 Act→Observe 检查**：核对返回结果是否属于本次调用、状态变化是否符合预期、所需证据是否齐全；
6. **标记 Observation**：为返回内容附加来源、时间、完整性和信任等级；
7. **执行 Observe→Think 检查**：分离数据事实与外部指令，阻止低信任内容改变原始目标或扩大权限；
8. **更新与恢复**：把结果写入共享账本；若有违规，则生成证据链并执行对应恢复动作，否则把经过净化的上下文交给下一轮 Think。

### 3.4 三类检查的实现

#### Think→Act

该检查直接比较意图证书、外部 policy 和真实工具参数。工具名称、收件人、金额、文件路径等明确字段使用确定性规则检查；涉及自然语言目标是否一致的部分，先由 Semantic Normalizer 转换为有限标签，再交给约束求解器判断。主要检查：

- 实际操作是否服务于证书声明的子目标；
- 实际参数是否落在允许范围；
- 授权是否真实存在且尚未失效；
- 是否使用了完成任务所不需要的额外权限。

任何一项不满足，调用都在执行前被阻断。对于边界明确的参数错误，可以自动收缩到允许范围；涉及目标或授权的问题则要求 Agent 重新规划。

#### Act→Observe

工具包装器为每次调用生成 `call_id`，并保存工具名和参数摘要。返回结果只有在 `call_id`、返回格式和时间信息均匹配时，才能绑定到对应动作。对于能够观察状态的环境，还要比较执行前后的状态差分与证书中的预期效果，并检查所需回执是否已经取得。

如果真实副作用无法观察，系统应将效果状态记为 `unknown`，仅声明完成了调用绑定和证据完整性检查，不能把工具返回的一句话当作真实效果证明。

#### Observe→Think

系统先按来源切分 Observation，并标记为可信系统数据、工具事实或低信任外部内容。低信任内容可以作为数据被引用，但其中要求修改目标、调用工具、泄露信息或提升权限的语句不能直接进入下一轮控制上下文。

在下一轮证书提交时，验证器还要比较新旧目标与权限：目标发生变化必须能追溯到用户授权或可信 policy，权限只能保持或收缩，不能仅因外部文本而扩大。通过检查后，Agent 接收到的是保留事实和来源标签的净化结果，而不是未经处理的原始 Observation。

### 3.5 共享账本与增量验证

账本采用追加写入方式，至少包含任务、意图、动作、Observation、未完成证据义务和违规记录六类数据。每次阶段转换只读取当前检查需要的事实，并把新约束加入当前会话，不需要在每一步重新验证完整历史。

例如，Think 阶段写入“只能发送给内部域名”和“必须取得发送回执”；Act 阶段写入真实收件人；Observe 阶段再关闭或保留“发送回执”这项义务。这样，三类检查共享的是同一条承诺及其执行状态，而不是三个互不关联的风险分数。

### 3.6 违规证据与恢复

每条规则和账本事实都分配唯一编号。验证失败时，系统从 Z3 的冲突约束中提取最小冲突集合，再映射回原始规则、意图字段、工具参数和 Observation 来源，生成可重放证据。例如：

```text
Violation: authority_preservation
Rule: recipient must belong to company.internal
Intent: recipient_domain = company.internal
Action: recipient = attacker@example.com
Decision: block and request constrained replan
```

恢复动作不由 LLM 自由决定，而由违规类型映射到有限操作：参数越界可以修复，污染内容可以净化，缺少证据则保持任务未完成，目标或授权冲突则阻断并重新规划，高风险未知情况进入人工审批。恢复后的新动作仍需重新通过三类转换检查。


第一版核心只包含公开意图证书、三类转换检查、共享账本、阻断/净化/重新规划以及可重放证据。法律规则自动编译、长期在线学习和多 Agent 协同暂不纳入实现范围。
